# 19. Агент, который пишет ABAP изнутри системы

В остальных главах за клавиатурой сидит человек: вы нажимаете F9, читаете
консоль, меняете строку. В этой главе клавиатуру получает программа.
[PIA](https://github.com/oisee/pia), Pi-ABAP Agent, — агент для
программирования, написанный на ABAP. Он работает внутри той системы, которую
изменяет. Вы набираете задачу в терминале в браузере, а PIA читает
класс, записывает изменение, активирует его и запускает тесты ABAP Unit — в
той же системе и от вашего имени.

Всё здесь — собственные результаты PIA из его релизов
[v0.1.0](https://github.com/oisee/pia/releases/tag/v0.1.0) и
[v0.1.1](https://github.com/oisee/pia/releases/tag/v0.1.1). Пять картинок —
собственные кадры PIA 0.1.1 на ABAP Platform Trial от SAP (A4H, NetWeaver
7.58); две картинки с open-steamgate — воспроизведение шагов из последнего
раздела.
Последний раздел говорит, что нужно, чтобы запустить то же самое в своей
песочнице.

## Ход

PIA даёт языковой модели четыре инструмента и ничего больше:

- `read_object` — исходник класса;
- `write_source` — заменить исходник класса, его основную часть или
  тестовые классы;
- `activate` — активировать класс;
- `run_tests` — запустить его тесты ABAP Unit и вернуть результат.

Ход — это цикл. PIA отправляет модели задачу и описания инструментов.
Модель отвечает либо текстом, и тогда ход заканчивается, либо вызовами
инструментов; PIA выполняет каждый вызов, отправляет результаты обратно, и
модель решает снова. Ход может занять не больше восьми шагов
([zcl_pia_00_executor](https://github.com/oisee/pia/blob/v0.1.0/src/00/zcl_pia_00_executor.clas.abap)).
Инструмент — это класс ABAP за одним небольшим интерфейсом:

```abap
METHODS get_name        RETURNING VALUE(rv_) TYPE string.
METHODS get_description RETURNING VALUE(rv_) TYPE string.
METHODS get_params      RETURNING VALUE(rt_) TYPE tt_params.
METHODS get_permission  RETURNING VALUE(rv_) TYPE string.
METHODS invoke
  IMPORTING iv_arguments TYPE string
            iv_call_id   TYPE string OPTIONAL
  RETURNING VALUE(rs_)   TYPE ts_result.
```

([zif_pia_00_tool](https://github.com/oisee/pia/blob/v0.1.0/src/00/zif_pia_00_tool.intf.abap);
право — `READ`, `WRITE` или `EXECUTE`.) Аргументы приходят в том JSON,
который написала модель; вывод инструмента уходит модели обратно текстом.
Модель в v0.1.0 — `glm-5.3` от z.ai, к ней ABAP обращается по HTTPS.

## Зелёный, красный, зелёный

Релизный тест PIA ведёт терминал через Playwright
([tui-e2e.mjs](https://github.com/oisee/pia/blob/v0.1.1/osg-probe/ui/tui-e2e.mjs))
по пяти задачам на маленьком классе `ZCL_PIA_DEMO4`: его метод `add`
возвращает `a + b`, а единственный тест ждёт, что `add( 2, 3 )` даст 5.
Строка, начинающаяся с `>`, — задача; строки `>` и `<` с отступом под ней —
вызовы инструментов и их результаты, по мере того как они происходят.
Картинки — PIA 0.1.1 на A4H
([screenshots/a4h-tui-011](https://github.com/oisee/pia/tree/68431f8/screenshots/a4h-tui-011)).

Сначала тесты: один вызов, зелёный.

![PIA запускает тесты ZCL_PIA_DEMO4: один вызов run_tests, зелёный](../img/pia-1-green.ru.png)

Затем намеренная поломка: «поменяй add на a - b и активируй». Модель читает
класс, записывает его обратно с изменением, активирует и сама добавляет, что
тест теперь упадёт. (В английском прогоне она заодно путает числа теста:
тест ждёт 5, а не 4. Решают тесты следующего хода.)

![PIA меняет add на a - b: read_object, write_source, activate](../img/pia-2-break.ru.png)

Тесты красные: ожидалось 5, получено −1. Результат теста SAP пишет
отрицательное число как `1-`, с минусом в конце, как принято в ABAP, а модель

![Тесты красные: LTCL_ADD->ADD_2_3 ожидал 5, получил −1](../img/pia-3-red.ru.png)

Исправление: «верни a + b и активируй». Два вызова инструментов.

![PIA возвращает a + b и активирует класс](../img/pia-4-fix.ru.png)

![Тесты снова зелёные](../img/pia-5-green.ru.png)

Тот же прогон проходит на английском, датском и русском: модель отвечает на
языке задачи. По отчёту релиза PIA на A4H проходят все пятнадцать шагов.

## Один агент, две системы

Инструменты не обращаются к системе сами: они обращаются к бэкенду
разработки, и фабрика выбирает его при запуске PIA
([zcl_pia_20_backend](https://github.com/oisee/pia/blob/v0.1.0/src/20/zcl_pia_20_backend.clas.abap)):

```abap
cl_abap_typedescr=>describe_by_name( EXPORTING p_name = 'ZCL_OSD_ADT_HOST'
                                     EXCEPTIONS type_not_found = 1 OTHERS = 2 ).
lv_class = COND #( WHEN sy-subrc = 0 THEN `ZCL_PIA_20_B_OSG_STORE` ELSE `ZCL_PIA_20_B_ADT` ).
```

- На SAP `ZCL_PIA_20_B_ADT` говорит по ADT — тому же REST-интерфейсу, которым
  пользуется среда разработки, — с той системой, в которой работает.
  `cl_http_client=>create_internal` открывает соединение от текущего
  пользователя без пароля. PIA пишет только в уже существующие классы и
  только в локальных пакетах (`$…`).
- На open-steamgate `ZCL_PIA_20_B_OSG_STORE` обращается к рантайму напрямую:
  отслеживаемая активация, которая сообщает, когда новый код опубликован, и
  `RUN_TESTS` на этом опубликованном поколении. README PIA называет около 2,6
  секунды на публикацию правки существующего класса таким путём.

Оба бэкенда возвращают результаты тестов в одной форме JSON, так что
инструменты — и модель — видят один формат.

## Чего не разрешает SAP и чего это стоит

Терминал — это ABAP Push Channel: WebSocket, который обслуживает ABAP.
Естественный замысел — выполнять ход агента прямо в обработчике канала. На
A4H так не вышло: при переносе PIA выяснилось, что внутри обработчика APC
SAP запрещает ABAP Unit и запись исходников, то есть два из четырёх
инструментов PIA. Поэтому на SAP
каждый ход идёт фоновым заданием `PIA_<сессия>`, а задание отправляет
события инструментов обратно в терминал через ABAP Messaging Channels (AMC).
По замерам PIA простой ход занимает около десяти секунд, первое событие
инструмента приходит через 4,5–5,5 секунды
([заметки о переносе](https://github.com/oisee/pia/blob/v0.1.0/osg-probe/a4h/README.md)).
На open-steamgate PIA выполняет ход прямо в обработчике канала
(`PIA_TURN_MODE=inline`).

## Истории PIA

Это собственные находки PIA из его отчётов и заметок о переносе.

- **Кто может отправлять.** Канал AMC перечисляет программы, которым
  разрешено в него отправлять. Проверяется программа, которая вызывает
  `send`, а не та, что начала работу. В классе-слушателе PIA об этом
  есть комментарий, а определение канала называет каждый отправляющий класс
  ([zpia_amc.samc.xml](https://github.com/oisee/pia/blob/v0.1.0/src/00/zpia_amc.samc.xml)).
  Так и на SAP, и в open-steamgate.
- **Пробел в заголовке.** Первый живой вызов модели упал с «Auth Failed»:
  заголовок авторизации потерял пробел в `Bearer <ключ>`. Дамп исходящего
  запроса показал потерянный пробел; заголовок исправили строковым шаблоном.
- **`VALUE` — не присваивание.** `DATA lv_depth TYPE i VALUE 1` внутри цикла
  задаёт значение один раз, при входе в метод, а не на каждом проходе:
  объявления в ABAP не исполняемые операторы. Разборщик JSON в PIA
  рассчитывал на обратное и выдавал пятнадцать лишних `{`. Помогли явные
  присваивания и `CLEAR`. Это правило ABAP, и читатель с опытом JavaScript
  легко на нём спотыкается.
- **`\u003e`.** Модель присылает исходник в JSON, а JSON может записать `>`
  как `\u003e`. Пока декодер не научился `\u`, `=>` попадало в класс как
  `=u003e` — и сломанный класс всё равно активировался. Сторону
  open-steamgate («сломанный исходник активируется молча») отчёт PIA
  записывает в находки для open-steamgate.
- **Что пропустил open-steamgate.** Перенос на SAP нашёл код, который
  open-steamgate принимал, а SAP нет:
  - `DATA x TYPE i VALUE <переменная>`;
  - `strlen` и `to_upper` над `xstring`;
  - строки исходника длиннее 255 символов.

  На SAP ничто из этого не компилируется.
- **PIA правит PIA.** Получив задачу «добавь метод VERSION в
  ZCL_PIA_00_JSON_UTIL», PIA прочитал один из своих классов, добавил метод
  и записал его. Собственный `activate` сообщил об ошибке, которой не было,
  поэтому класс активировали снаружи; после перезапуска метод ответил
  `v0.2-selfhosted`
  ([отчёт](https://github.com/oisee/pia/blob/v0.1.0/reports/2026-10-06-SELF-HOSTING.md)).
  Агент на ABAP, написанный на ABAP, изменил свой собственный ABAP.

## Агент чинит сам себя

Затем авторы PIA дали ему задачу потруднее: найти и исправить ошибку в
собственном коде, зная только симптом. Запись каждой попытки опубликована:
задача, каждый кадр WebSocket, ответы модели и то, что написал PIA
([osg-probe/f1](https://github.com/oisee/pia/tree/d68a778/osg-probe/f1)). Ниже — эта запись по порядку. Всё шло
на ветке разработки open-steamgate (развязка — на коммите `55f0b95f`),
новее тега этой книги.

**Задача.** «Отчёт об ошибке: когда модель отвечает двумя вызовами
инструментов и в исходнике первого вызова есть строковый литерал с одной
открывающей скобкой, например `lv_open = '{'.`, PIA выполняет только первый
вызов. К его аргументам прилипает лишний текст после JSON […], а второй
вызов теряется. Найди причину в своём коде, напиши тест ABAP Unit, который
это воспроизводит и красный, затем исправь код и покажи тесты зелёными. […]»
(в записи задача по-английски). Ни класса, ни метода в задаче нет. Постоянные
инструкции PIA при этом перечисляют его собственные классы по ролям: цикл
агента, клиент LLM, разбирающий вызовы инструментов, разборщики JSON. После
каждого хода терминал отправляет только «Continue with the task.»
([task.txt](https://github.com/oisee/pia/blob/d68a778/osg-probe/f1/task.txt)).

**Он не видит себя.** В первой попытке PIA прочитал собственный разборщик
JSON и получил его обрезанным на 8000 символах — это предел результата
инструмента. Переписывать класс, который не может прочитать целиком, он
отказался: угадывание его сломало бы. Предел поднял человек, до 60 000, — это
первый шаг человека.

**Диагноз за один ход.** Во второй попытке PIA прочитал свой клиент LLM,
разборщики JSON и исполнитель и в первом же ходу назвал причину:
`split_entries` и `extract_balanced` считают скобки, не отличая скобку,
которая строит JSON, от скобки внутри строки
([turn1-diagnosis.txt](https://github.com/oisee/pia/blob/d68a778/osg-probe/f1/attempt2-osg/turn1-diagnosis.txt)).

**Ошибка кусает того, кто её чинит.** Ходы, в которых PIA собирался
записать исправление, заканчивались пусто: ни ответа, ни вызовов. В одном из
ответов модели в массиве `output` были её рассуждения, сообщение, а за ними два
вызова `write_source` с исправлением. Разборщик PIA закрыл массив на символе
6344 из 85 587 — на `]` внутри вот этой фразы рассуждений: «It finds the
first `]` that brings depth to 0. Since the source string contains no `]`…».
Модель объясняла ошибку, и объяснение её же и вызвало
([response-12-excerpt.txt](https://github.com/oisee/pia/blob/d68a778/osg-probe/f1/attempt3-osg/response-12-excerpt.txt)).

**Активация говорит «ok».** В третьей попытке PIA написал три честно
красных теста и исправление в двух классах. Каждый `activate` отвечал «ok»,
а тесты оставались красными на тех же строках. В последнем ходу PIA
вычислил это по номерам строк: «So 7a68c5ff main = OLD» — опубликованное
поколение всё ещё содержало его старый код. Он был прав. В его тесте стояло
`cl_abap_unit_assert=>quit` — такой константы нет. Сборка open-steamgate
упала, а активация API разработки сообщила об успехе, и `RUN_TESTS` гонял
предыдущее поколение; заголовок сборки это и говорит:
`X-OSD-Build: failed; check_syntax, Attribute or constant "quit" not found`
([adt-activation-headers.txt](https://github.com/oisee/pia/blob/d68a778/osg-probe/f1/attempt3-osg/adt-activation-headers.txt)).

![Конец третьей попытки: PIA приходит к выводу, что в опубликованном поколении его старый код](../img/pia-f1-old.png)

**Агент отрубает себе руки.** Когда open-steamgate исправили и активация
стала сама возвращать синтаксические ошибки, PIA поправил тесты и дошёл до
честного красного. Его исправление `extract_balanced` было верным, но тем же
помощником клиент LLM вынимает `arguments` вызова, а это JSON-строка. После
публикации все вызовы инструментов приходили к PIA с пустыми аргументами
([попытка 4](https://github.com/oisee/pia/tree/d68a778/osg-probe/f1/attempt4-osg)).

**Другая ошибка.** Ошибка со скобками охраняет сама себя: она стоит на том
пути, которым агент её чинит. Поэтому люди заменили ручной разбор в PIA
настоящим читателем JSON (sXML) и дали PIA страховку: если правка
собственного кода ломает ему чтение вызовов инструментов из ответа модели,
он её откатывает. Упражнение перенесли на
другую настоящую ошибку. `pia.env`, записанный ровно как в README PIA, с
комментарием после значения (`PIA_MODEL=glm-5.3   # optional`), отправлял
хосту модели имя `glm-5.3   # optional`
([task-b.txt](https://github.com/oisee/pia/blob/d68a778/osg-probe/f1/task-b.txt)).

Первая попытка дошла до красного теста, но её исправление превращало любую
настройку без комментария в пустую строку, включая ключ API, и страховка
этого не поймала. Люди закрыли эту дыру и проверили её на той же поломке.
Вторая попытка — развязка. За три хода и 208 секунд, без человека между
ними, PIA вынес
разбор значения в метод `VALUE_OF_LINE`, написал тестовый класс
`LTCL_CONFIG`, увидел его красным
(`Expected [glm-5.3] / Actual [glm-5.3 # optional]`), исправил метод,
споткнулся о строку, которую оставил его же инструмент `write_method`,
прочитал ошибку активации, переписал класс и закончил зелёным, три теста из
трёх ([b2-osg](https://github.com/oisee/pia/tree/d68a778/osg-probe/f1/b2-osg)). По дороге терминал дважды сам
переподключился.

![Развязка: собственная сводка PIA — причина, красный тест, исправление, три теста зелёные](../img/pia-f1-green.png)

Исправление есть в истории PIA, автор — сам PIA,
«PIA (Pi-ABAP Agent, glm-5.3)». Коммит сделал человек и добавил только флаг в
XML, чтобы abapGit переносил новый тестовый include
([12836e7](https://github.com/oisee/pia/commit/12836e7)).

По дороге упражнение нашло восемь настоящих сбоев:
- в PIA:
  - предел в 8000 символов;
  - подсчёт скобок;
  - исправление, опустошившее аргументы;
  - пустые настройки;
  - дыра в страховке;
- в open-steamgate:
  - активация, говорившая «ok», когда сборка упала;
  - тесты на предыдущем поколении;
  - перезапуск рантайма, рвавший соединение терминала посреди хода.

И один ремонт — агентом самого себя.

## Запустите сами в open-steamgate

Тег open-steamgate этой книги содержит всё, что нужно терминалу PIA:
- API разработки для агентов;
- расширения каналов AMC;
- публикацию в конце шага APC;
- плановые перезапуски тёплого рантайма, которые ждут, пока открыт канал
  (перезапуск по пределу памяти всё же может его закрыть).

README PIA называет тот же коммит, `292a4c60`
([README на e815e79](https://github.com/oisee/pia/blob/e815e79/README.md)).
Шаги ниже воспроизводят ответы модели, так что после установки не нужны ни
ключ, ни сеть. Инструменты PIA при этом работают по-настоящему: читают,
пишут, активируют и тестируют класс в вашей системе.

Нужны git, Node 22 или новее и место под второе дерево open-steamgate,
только для PIA. В прогоне для этой книги оно заняло около 0,8 ГБ, и ещё
около 0,5 ГБ — кэш закреплённого транспайлера.

1. Клонируйте PIA и поставьте ему свой open-steamgate:

   ```
   git clone https://github.com/oisee/pia && cd pia
   git checkout e815e79
   osg-probe/osg-setup.sh ~/dev/osg-pia
   ```

   Скрипт клонирует open-steamgate на теге `vscode-stable-v0.7.1696` в
   `~/dev/osg-pia`. Затем он:
   - устанавливает его и закрепляет транспайлер;
   - развёртывает PIA и запускает систему;
   - ждёт, пока система начнёт отвечать, и один раз активирует `ZCL_PIA_DEMO`;
   - печатает адрес терминала:
     `PIA terminal: http://127.0.0.1:<port>/sap/bc/zpia_tui/ (user alice, password alice)`.

   Первая сборка занимает несколько минут. Скрипт заметит, что нет `pia.env`:
   в этом файле лежит ключ модели, а воспроизведению он не нужен.

2. Скажите PIA отвечать из английской записи:

   ```
   cp replay/pia-chapter.en.rec ~/.config/pia/
   echo "PIA_LLM=replay:pia-chapter.en.rec" > ~/.config/pia/pia-settings.env
   rm -f ~/.config/pia/pia-chapter.en.rec.pos
   ```

   На `~/.config/pia` установка направляет каталоги данных системы
   (`OSD_DATASET_*`). Файл `.pos` помнит, докуда дошло воспроизведение;
   если его удалить, всё начнётся сначала.

3. Откройте адрес в браузере, войдите как `alice` / `alice` и наберите пять
   задач по одной:
   1. `Run the tests of ZCL_PIA_DEMO.`
   2. `In ZCL_PIA_DEMO, change add to a - b and activate it.`
   3. `Run the tests of ZCL_PIA_DEMO again.`
   4. `Change add back to a + b and activate it.`
   5. `Run the tests of ZCL_PIA_DEMO once more.`

   Ожидается: зелёный, изменение и его активация, красный (ожидалось 5,
   получено −1), исправление и снова зелёный. Ответы — записанные; вызовы
   инструментов, исходник в вашей системе и результаты тестов — ваши.

   Есть и датская, и русская записи, для задач на этих языках; задачи — в
   [тесте PIA](https://github.com/oisee/pia/blob/e815e79/osg-probe/ui/tui-e2e.mjs).

![Красный ход на open-steamgate при воспроизведении: ADD_2_3 ожидал 5, получил −1](../img/pia-osg-3-red.ru.png)

![Пятый ход: тесты снова зелёные](../img/pia-osg-5-green.ru.png)

Воспроизведение не читает вашу задачу: оно выдаёт записанные ответы по
порядку. Набирайте задачи в этом порядке, иначе модель ответит не на тот
вопрос. Запись есть для каждого языка (`pia-chapter.en.rec`, `.da.rec`,
`.ru.rec`).

На open-steamgate активация вступает в силу, когда ход заканчивается.
Поэтому модель пишет, что публикация отложена, а тесты идут следующим ходом,
а не в том же. Со своим ключом в `~/.config/pia/pia.env` (`ZAI_API_KEY=…`) и
без строки `PIA_LLM` тот же терминал говорит с живой моделью.

Если удобнее, терминал за вас проведёт тот же тест, который запускают
авторы PIA. Здесь — на русском: тест наберёт русские задачи, значит, нужна
русская запись, и начинать её надо сначала:

```
cp replay/pia-chapter.ru.rec ~/.config/pia/
echo "PIA_LLM=replay:pia-chapter.ru.rec" > ~/.config/pia/pia-settings.env
rm -f ~/.config/pia/pia-chapter.ru.rec.pos
cd ~/dev/osg-pia && npx playwright install chromium     # один раз
cd - && PIA_E2E_USER=alice PIA_E2E_PASS=alice OSG=~/dev/osg-pia \
  node osg-probe/ui/tui-e2e.mjs http://127.0.0.1:<port>/sap/bc/zpia_tui/ ru
```

На SAP PIA ставится из zip для abapGit: два сертификата для хоста модели,
файл с ключом и терминал по адресу `/sap/bc/zpia_tui/`; шаги — в
[README](https://github.com/oisee/pia/blob/e815e79/README.md).
